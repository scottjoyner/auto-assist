# AssistX Tailnet sanitizing Caddy — exact unit cutover

**2026-10-23 | PR #425 | ingress issue #149 | not proof of the broader Hermes release**

The previously unsafe raw forwarding is `control-room-ts-proxy.service` (`socat`), forwarding x1-370's Tailscale `100.64.43.123:8000` to the local AssistX API. The backend still trusts a configured `Tailscale-User-Login` header, so raw Tailnet input must not reach it without stripping. Separately authenticated Tailscale Serve mobile SSO at HTTPS :8443 must remain untouched. Hermes writable-mount P0 #414 is a separate deployment blocker.

New `scripts/systemd/assistx-tailnet-sanitizer.service` and `scripts/systemd/assistx-tailnet-sanitizer-fallback.service` are two distinct user-systemd services with `NoNewPrivileges`, independent exact SHA-256 config manifests, the same pinned Caddy executable, and Caddy validation on every start. The primary and fallback must **not run simultaneously**, because both require the same exact Tailnet socket. The fallback is to **sanitizing Caddy**, never socat. The primary/fallback config files are staged at `/home/scott/.config/assistx-tailnet-sanitizer/` and both must SHA-256 match `c4136364469a45f918c8e9a33ce5268f57dc4ee39b030012af4f66aaf9b186b2`; `/usr/bin/caddy` must match `9681d054b6e5137d53f6d027188b349e0603fd12ea6334bd0d49da6755432f1b`.

The guarded script `scripts/assistx_tailnet_live_cutover.sh` is **inert by default**. Its `--execute-live` mode checks host, exact pinned revision ancestry, clean Git checkout, Tailnet address, active legacy and inactive replacement services, three SHA manifests, adapted strict listener with/without environment, exact preflight, and API health. Only then does it disable the raw forwarder's boot enablement, stop it, and enable/start primary Caddy. It requires the postcutover kernel socket-ownership attestation, real Basic status-only GET (anonymous 401, forged identity-only 401, real Basic 200, mixed Basic 200), and independently authenticated mobile whoami SSO. A failure after traffic handover disables/stops primary and enables/starts only the pinned fallback; an unavailable fallback means fail-closed/offline, never restored raw socat. Both services are non-root user units.

Post-cutover proof still requires verified production endpoint health, off-host authorized-client continuity, correct cgroup/UID/inode, legacy boot fence across daemon reload and approved reboot, and evidence the fallback itself works on the true production port. The postcutover static attestation deliberately always says `decision=HOLD`, even when metadata qualifies. A passing ingress switch does not approve Hermes writable mount isolation, signed user custody, task receipts, revocation or other release gates. Never mark issue #149 or #414 resolved without their own criteria.
