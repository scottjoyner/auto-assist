# P0: Tailnet-forwarded legacy AssistX trusted-header ingress — October 22, 2026

**Disposition: HOLD / NO-GO for production Hermes/AssistX release.** Draft PR #425 and security issue #414 remain open. The changes in this slice are source code, synthetic tests and read-only qualification; no production proxy, firewall, Tailscale ACL, environment variable, container image, Docker service, model or NAS data was changed.

## Verified live trust chain on x1-370

Fleet Commander observed a running **user-level systemd service `control-room-ts-proxy.service`**, whose active main process is `socat`, forwarding the x1-370 **Tailscale IPv4 address on TCP port 8000 to localhost TCP port 8000**. The running `assistx-api` container itself publishes Docker port 8000 only on 127.0.0.1. Anonymous GET requests to **both** local and Tailnet `/openapi.json` returned HTTP 200, the same 151,719-byte schema fingerprint, and the exact AssistX task/claim route catalog. Both anonymous GETs to a synthetic nonexistent executor-claim status route returned HTTP 401. No forged authentication header was sent and no task data was read.

The production AssistX configuration has **`TRUSTED_AUTH_HEADER` set**, while signed-gateway owner enforcement and the emergency rejection described below are disabled. Its checked-in `api.py::_auth_user_from_credentials` historically accepted a nonempty value from that configured header **ahead of Basic credentials**, without verifying a signed gateway assertion in legacy mode. Since `socat` is a raw TCP forwarder and not a header-sanitizing authenticated gateway, a Tailnet client that knows or guesses the trusted header name **may be able to impersonate an API user** on routes protected only by `auth`. A fully authorized live header-spoof login test was intentionally not performed. The Tailnet ACLs and reachable client set were not established, so this is a **verified network-to-trusted-header trust path and conditional spoofing risk**, not a claimed public-Internet exposure or demonstrated unauthorized access.

## Reversible mitigation implemented but NOT deployed

In the source-only candidate, `src/assistx/api.py` supports the exact opt-in configuration **`ASSISTX_REJECT_LEGACY_TRUSTED_HEADER=true`** independently of the unfinished signed-gateway mode. When this is true, a nonempty legacy trusted-user header causes authentication failure. There is **no downgrade to Basic** if a hostile header is present, even when valid Basic credentials accompany it. Basic authentication **without** the header still works, preserving that existing path. With the new flag absent, legacy behavior remains unchanged; the existing stricter signed-gateway mode still binds a trusted header to a valid signed canonical owner. The source-only emergency flag does not affect the running container until an image with the change has been built, pinned and carefully deployed with the flag.

A separate non-mutating `tests/hermes_live_api_owner_gate_preflight.py --physical-readonly` check independently verifies all of the following without printing header names/values, credentials, public addresses, task IDs or secrets: live AssistX route/status, loopback-only Docker publication, configured legacy-header trust, emergency rejection flag, active `control-room-ts-proxy.service` with exact Tailnet→loopback `socat` chain, and equality of bounded public OpenAPI schema fingerprints over local and Tailnet GET. Any unavailable verification is reported as **unknown**, never as proof of safety. Production promotion remains false even if a mitigation flag is present; the authenticated signing gateway and independent witness are separate requirements.

## Smallest safe operational cutover (not executed)

First inventory which authorized workbench/mobile/agent clients actually depend on header-only authentication through the Tailnet TCP:8000 forwarder. Prefer retiring the raw TCP:8000 forward in favor of a genuinely authenticated edge that **strips incoming client identity headers and reissues them only after verified authentication**, or removing production `TRUSTED_AUTH_HEADER` entirely when those clients can use validated Basic authentication. If service compatibility requires a staged migration, build/pin a new AssistX API image with `ASSISTX_REJECT_LEGACY_TRUSTED_HEADER=true` in a disposable canary, verify a direct unauthenticated/header-only request is denied while valid Basic without the header is accepted, and prepare an exact rollback before any production deployment. **Do not just flip the new variable in the current image:** it has not been deployed, and the current container would not enforce it. Do not stop `control-room-ts-proxy.service` without first mapping its dependencies and a rollback plan.

No user authenticating via the legacy header should lose access as an unmeasured side effect of this research pass. Until a qualified ingress mitigation and verified independent signing/rollback custody exist, retain all production HOLDs: genuine two-user owner-bound claims/receipts/partition fencing, a safe RO corpus/RW scratch migration away from 16 mounts, immutable image signing, and rollback readiness.

## Validation boundaries

Synthetic ASGI tests compile the exact checked-in `_auth_user_from_credentials` source from `api.py` without importing the production application. They verify exact lowercase flag semantics, bare-header rejection, no Basic downgrade with a hostile header, unchanged Basic with no header, unchanged legacy mode when disabled, and interaction with the signed-owner mode. Preflight test fixtures cover confirmed Tailnet ingress, emergency flag on/off and evidence-unavailable results. **This is not proof the unmodified live API rejects a spoofed trusted header.** The live ingress risk persists until a tested operational mitigation is applied.


## Image-provenance clarification

A configured emergency-rejection flag alone cannot prove the live container actually contains the new guard. The read-only preflight therefore reports legacy_header_tailnet_spoof_risk = null (UNKNOWN, not safe) when the flag is present but the runtime is unqualified, and legacy_header_runtime_containment_verified = false until an exact-image authenticated acceptance canary is complete. Verified risk is TRUE for the current live forwarder and legacy header with no guard configured. NO-GO remains in both cases.
